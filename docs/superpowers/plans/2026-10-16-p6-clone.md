# P6 Clone Implementation Plan

> **For agentic workers:** Executed natively by the session that wrote it (user delegated execution:
> "build plan is up to you... let me know when everything is done"). Steps use `- [ ]` tracking.

**Goal:** Local Electron app that behaves like Primavera P6 Professional for XER/XML import,
scheduling, progressing, resources, costs, leveling, export.

**Architecture:** `core/` pure TypeScript domain logic over a DB of raw P6 tables; `cli/` wraps
core; Electron `main/` = window, native menu, dialogs, file IO, atomic DB persistence;
`renderer/` = React UI that holds the DB in memory and runs core directly.

**Tech Stack:** Node 24 (native TS type stripping, `node --test`), TypeScript (typecheck only),
Electron, React, Vite, esbuild (main/preload bundle), Playwright (`_electron` smoke tests).

**Spec:** `docs/superpowers/specs/2026-10-16-p6-clone-design.md`

## Global Constraints

- Core/CLI/tests run directly on Node 24 `.ts` (erasable syntax only: no `enum`, no parameter
  properties, no namespaces; imports use `.ts` extension). `tsc --noEmit` must pass.
- Row values are stored as raw XER strings; never lose a field or table on import→export.
- Fields whose name starts with `_` are clone-internal and are never written to XER.
- Dates: P6 format `yyyy-mm-dd hh:mm`; internal times = minutes since 1970-01-01 treating the
  wall-clock as UTC (no DST, no TZ).
- XER output: CRLF, Windows-1252, `%E` terminator, header
  `ERMHDR\t<ver>\t<yyyy-mm-dd>\tProject\t<user>\t<user name>\tdbxDatabaseNoName\tProject Management\t<curr short name>`.
- Fixtures under `Sample XERs/` are read-only and byte-exact (`*.xer binary` in git).
- No commercial UI libraries. Minimal dependencies.

## Decision log (deviations from spec, made autonomously)

- Renderer owns the in-memory DB and runs core directly; main only persists (atomic write of the
  JSON snapshot it receives, debounced 800 ms). Simpler than IPC-synchronised tables; a renderer
  crash loses at most the last debounce window. Spec §3.2/§15 intent (atomic, no corruption) kept.
- Schema field lists for versions seen in real P6 samples are extracted from those samples
  (`verified: true`). Modern versions = latest verified list + documented additions (`verified: false`).
- Version keys are the exact ERMHDR strings (5.0, 5.0.2000, 6.0, 6.0.0, 6.2, 7.0, ...). Export
  version list in UI: 5.0, 6.0, 6.2, 7.0, 8.1, 8.2, 8.3, 8.4, 15.1, 15.2, 16.1, 16.2, 17.12, 18.8,
  19.12, 20.12, 21.12, 22.12, 23.12, 24.12.

### Added during the build (learned from the real P6 samples)

- ERMHDR version labels the *export format*; field layouts follow the P6 build. Variants per version are kept and the
  source layout is reused when it matches a known variant (all 25 real files re-export byte-identical).
- Validator calibrated on real exports: relationship loops and duplicate same-type links are warnings (real P6
  exported them), `PR_FS1`-style codes are legacy warnings, `%E` before later tables is an error (P6 stops reading).
- Scheduler rules discovered from oracle mismatches: project calendars inherit holidays from `base_clndr_id`; not-started
  work floors at max(data date, planned start); planned dates follow early dates for not-started activities;
  completed activities are zero-length nodes at max(data date, open-logic date) and lags from them count from actuals;
  under Retained Logic start links to/from in-progress activities use the remaining start.
- Import of a P6-fatal file is refused (like P6); files with P6 *errors* are imported anyway with a warning so they can
  be inspected — the Import Log states what real P6 would do.
- Renderer bundle is not minified: the minifier reordered module initialisation and broke startup; size is irrelevant locally.
- Enterprise dialogs and the Resources/Assignments windows were written by parallel subagents against this plan's conventions.

## Review Focus

1. Agent XER with LF endings / UTF-8 / missing `%E` / ragged rows → imports with warnings where P6
   tolerates, never crashes (fixture test over all samples asserts no throw).
2. Relationship loops and self-links → scheduler aborts with loop members listed, DB untouched.
3. Calendars with zero work days or exceptions covering whole range → scheduler stops searching
   after a bounded horizon (20 years) and reports the activity instead of hanging.
4. In-progress activities with actual start after data date / missing actual start → validator
   warns and scheduler treats per P6 (actual dates win; data date not moved).
5. Export of a project referencing dictionaries (calendar/resource) not in DB → writer emits only
   existing rows, validator on re-import flags dangling refs; no throw.

## Core types (Produces, used everywhere)

```ts
// core/db.ts
export type Row = Record<string, string>;
export interface Table { name: string; fields: string[]; rows: Row[] }
export interface XerHeader { version: string; exportDate: string; raw: string[] }
export interface Db { header?: XerHeader; tables: Record<string, Table> }
export function table(db: Db, name: string): Table               // creates empty if missing
export function rows(db: Db, name: string): Row[]
export const KEYS: Record<string, string>                        // TASK->task_id ...
export function refTarget(field: string): string | undefined     // 'pred_task_id' -> 'TASK'
export function nextId(db: Db, tableName: string): number

// core/findings.ts
export type Severity = 'fatal' | 'error' | 'warning' | 'info';
export interface Finding { severity: Severity; code: string; message: string; p6: string;
  table?: string; row?: number; key?: string; field?: string }
```

## Milestone 1 — XER core + CLI

### Task 1.1: Project scaffold + dates/encoding
Files: package.json (`"type":"module"`, scripts `test`=`node --test tests/`, `typecheck`=`tsc --noEmit`),
tsconfig.json (`erasableSyntaxOnly`, `allowImportingTsExtensions`, `noEmit`, `strict`,
`module: nodenext`, `jsx: react-jsx`), core/dates.ts, core/encoding.ts, tests/dates.test.ts.
- `parseP6Date(s: string): number | null` ('' → null; accepts `yyyy-mm-dd hh:mm`, `yyyy-mm-dd`).
- `formatP6Date(m: number | null): string`.
- `serialToMinutes(d: number): number` (OLE serial, 0 = 1899-12-30; 41519 = 2013-09-02, US Labor Day),
  `minutesToSerial(m: number): number`.
- `decodeText(b: Uint8Array): {text: string; encoding: 'utf-8-bom'|'utf-8'|'windows-1252'}` —
  BOM → utf-8; valid UTF-8 with any byte ≥0x80 → utf-8; else windows-1252 (TextDecoder).
- `encodeCp1252(s: string): Uint8Array` (unmappable → `?`).
Tests: round-trip dates; serial 41519 ↔ 2013-09-02 00:00; cp1252 '€' ↔ 0x80.

### Task 1.2: Parser
`parseXer(bytes: Uint8Array): { db: Db; findings: Finding[]; meta: { encoding; lineEnding: 'CRLF'|'LF'|'mixed'; hasEnd: boolean } }`
- Never throws. Structural findings: `NO_HEADER` (fatal), `LF_ENDINGS` (warning; P6 writes CRLF,
  P6 import accepts), `NO_END` (warning), `ROW_BEFORE_FIELDS` (error, row skipped),
  `FIELD_COUNT` (error when row has more values than fields; fewer → pad, warning), `DUP_TABLE`
  (warning, rows appended), `ENCODING_UTF8` (info).
Tests: tests/parse.test.ts — synthetic XER strings for each finding; every file in `Sample XERs/`
parses without throw and every real-P6 file yields zero error/fatal findings.

### Task 1.3: Schema extraction + schema module
- scripts/extract-schema.ts: for real-P6 samples (header user name not in
  `['White Hat IQ Scheduler','NordBuild','NordBuild Oy','NordBuild Scheduling','AuroraSubA','Polaris DC-1','P6 User','ECC-BK-CS']`
  and ERMHDR not '12.0'), collect per version per table the field list (first seen; report
  conflicts), and a merged table order (topological merge of per-file orders). Writes
  `core/xer/schema-observed.json` `{versions: {[ver]: {[table]: string[]}}, tableOrder: string[]}`.
- core/xer/schema.ts:
  - `EXPORT_VERSIONS: string[]` (list in decision log).
  - `fieldsFor(version: string, table: string): string[] | undefined` — exact observed version;
    else nearest lower observed; for versions ≥ 8 start from 7.0 list and apply `MODERN_ADDITIONS`
    (below); undefined for unknown tables.
  - `isVerified(version: string): boolean`.
  - `TABLE_ORDER: string[]` (observed + modern tables appended).
  - `ENUMS: Record<string /* table.field */, string[]>` for task_type, status_code, duration_type,
    complete_pct_type, pred_type, cstr_type(2), rsrc_type, clndr_type, def_duration_type,
    sched_float_type, sched_outer_depend_type, sched_calendar_on_relationship_lag, critical_path_type.
  - `FIELD_TYPES`: derive by name: `*_date`→date, `*_flag`→flag(Y/N), `*_hr_cnt|*_qty|*_cost|*_pct|*_num`→number,
    `*_id`→id.
  - `MODERN_ADDITIONS` (verified:false): TASK: `est_wt` after `rev_fdbk_flag` (8.1+),
    `location_id` (15.1+), `crt_path_num` (19.12+) appended; TASKPRED: `comments` after `lag_hr_cnt` (8.1+);
    PROJECT: `cost_qty_recalc_flag`... keep 7.0 list + `location_id` (15.1+); TASKRSRC: `rsrc_type` etc as 7.0.
Tests: fieldsFor('7.0','TASK') length 58 starting `task_id`; fieldsFor('19.12','TASK') contains `est_wt`;
TABLE_ORDER puts PROJECT before PROJWBS before TASK before TASKPRED.

### Task 1.4: Writer
`writeXer(db: Db, opts: { version: string; projIds?: string[]; user?: string; userName?: string; exportDate?: string }): Uint8Array`
- Tables in TABLE_ORDER then any others alphabetically; field list = `fieldsFor(version, table)`
  ?? table's own non-`_` fields; rows filtered to `projIds` (by proj_id or via task/wbs ref) plus
  dictionary rows referenced by kept rows (calendars, resources, roles, accounts, codes, UDF types,
  currencies, units, OBS, memo types); empty tables omitted. CRLF, cp1252, `%E`.
- Default header user `admin`/`admin`, currency from first CURRTYPE `curr_short_name` or `USD`.
Tests: for each real-P6 sample, `writeXer(parse(f).db, {version: header.version, exportDate: header.exportDate, user, userName})`
equals original bytes after replacing header line (tolerated: header identical when same inputs).
Record the files that do not round-trip identically and why in the test as known exceptions (must be ≤ 3 and explained).

### Task 1.5: Validator
`validateXer(db: Db, parseFindings: Finding[]): Finding[]` (returns all, sorted fatal→info).
Rules (code — severity — p6 behaviour):
- `VERSION_UNKNOWN` warning (12.0 etc) "P6 imports by field name; version unknown to P6 releases".
- `NO_PROJECT` fatal, `NO_TASK` warning, `NO_PROJ_NODE` fatal (PROJWBS row with proj_node_flag=Y per project).
- `MISSING_KEY_FIELD` fatal (table lacks its KEYS field), `FIELD_UNKNOWN` warning with suggestion
  (Levenshtein ≤ 3 against all known field names of that table across versions, e.g. taskpred_id → task_pred_id),
  `MISSING_FIELD` info for verified fields absent (P6 fills defaults).
- `BAD_DATE`, `BAD_NUMBER`, `BAD_FLAG` error (P6 import fails / field rejected), `BAD_ENUM` error.
- `DUP_KEY` fatal; `DUP_TASK_CODE` error.
- `DANGLING_REF` error (P6 import fails on unresolved TASK→PROJWBS/TASKPRED→TASK); for clndr_id →
  warning "P6 assigns project default calendar".
- `WBS_CYCLE` fatal; `WBS_ORPHAN` warning.
- `CAL_PARSE` error, `CAL_NO_WORK` warning, `CAL_HOURS_MISMATCH` info.
- `REL_SELF` error, `REL_DUP` warning, `REL_LOOP` error ("P6 imports; scheduling fails").
- `ACT_DATES_ORDER` error (act_end < act_start), `STATUS_MISMATCH` warning (TK_Complete without
  act_end_date etc.), `ACTUAL_AFTER_DD` warning (actuals after project last_recalc_date).
- `MILESTONE_DURATION` warning (milestone with duration > 0).
Tests: tests/validate.test.ts one synthetic case per code; snapshot test `tests/fixtures-diagnostics.test.ts`
writes/compares `tests/__snapshots__/diagnostics.json` (code counts per file); real-P6 files: zero fatal/error.

### Task 1.6: CLI validate/export/diff
`cli/p6clone.ts` commands: `validate <file> [--json]` (exit 0 clean/warnings, 1 errors, 2 fatal),
`export <file> --version v --out path`, `diff a b [--json]` using `diffDbs(a: Db, b: Db): DiffEntry[]`
(`{table, key, field?, kind: 'added'|'removed'|'changed', a?, b?}`) in core/diff.ts.
Tests: tests/cli.test.ts spawns `node cli/p6clone.ts validate "Sample XERs/Tower-A.xer" --json`, parses JSON.

## Milestone 2 — Calendars + scheduler

### Task 2.1: clndr_data
`parseClndrData(s: string): CalendarDef` / `serializeClndrData(c: CalendarDef): string`
```ts
interface Shift { start: number; end: number }   // minutes from midnight; end 0 → 1440
interface CalendarDef { week: Shift[][] /* index 0=Sunday..6 */; exceptions: Map<number /*serial day*/, Shift[]> }
```
Generic tree parser for `(0||name(k|v|k|v)(children))`, tolerant of whitespace/newlines.
Tests: sample row from DHBL (Mon–Fri 08:00–16:00, 24 holidays); every CALENDAR row in all samples parses
(collect failures → test lists them; real-P6 must be zero).

### Task 2.2: WorkCalendar
```ts
class WorkCalendar { constructor(def: CalendarDef)
  shiftsOn(dayMinute: number): Shift[]; isWorkTime(t: number): boolean
  nextWorkStart(t: number): number; prevWorkEnd(t: number): number
  addWork(t: number, minutes: number): number   // from nextWorkStart(t); lands on end of work (17:00 not 08:00)
  subWork(t: number, minutes: number): number   // from prevWorkEnd(t); lands on start of work
  workBetween(a: number, b: number): number }
```
24-hour calendar helper `WorkCalendar.continuous()`. Horizon 20 years → throws `CalendarHorizonError`.
Tests: Fri 16:00 + 8h on Mon–Fri 08–16 = Mon 16:00; addWork(Fri 16:00, 0) = Fri 16:00;
subWork(Mon 16:00, 8h) = Mon 08:00; holiday skip; workBetween symmetric; no-work calendar throws.

### Task 2.3: CPM
`scheduleProjects(db: Db, projIds: string[], opts?: Partial<SchedOptions>): ScheduleResult`
```ts
interface SchedOptions { dataDate?: number; logic: 'retained'|'override'|'actual';
  floatType: 'start'|'finish'|'smallest'; lagCalendar: 'predecessor'|'successor'|'24h'|'project';
  openEndedCritical: boolean; ignoreExternal: boolean; useExpectedFinish: boolean;
  criticalBy: 'float'|'longestPath'; criticalFloatHrs: number }
interface ScheduleResult { ok: boolean; log: string; findings: Finding[]; stats: {activities: number; relationships: number; finish: number | null} }
```
Options default from SCHEDOPTIONS/PROJECT rows (sched_retained_logic Y→retained, sched_progress_override Y→override;
sched_float_type FT_FF? → see mapping in schema ENUMS doc comment; critical_path_type CT_DrivPath → longestPath).
Algorithm: build nodes (TASK of projIds), edges (TASKPRED; external preds/succs use
external_early_start_date/external_late_end_date unless ignoreExternal), Kahn topo sort → loops abort (DB untouched).
Forward pass per spec §7 (ES snapped by nextWorkStart; finish milestones = prevWorkEnd(nextWorkStart(t));
completed = actuals; in-progress remaining from data date honoring logic mode; constraints
CS_MSO/CS_MSOA/CS_MSOB/CS_MEO/CS_MEOA/CS_MEOB/CS_MANDSTART/CS_MANDFIN/CS_ALAP, secondary constraint).
Backward pass from Must Finish By (PROJECT.plan_end_date) else max EF. LOE after main passes; WBS summary
spans its WBS subtree. TF per floatType in hours of the activity calendar; FF; driving relationships;
longest path from latest-finishing activity back via driving rels.
Writes TASK: early_start_date, early_end_date, late_start_date, late_end_date, restart_date, reend_date,
rem_late_start_date, rem_late_end_date, total_float_hr_cnt, free_float_hr_cnt, driving_path_flag,
target dates untouched; PROJECT: scd_end_date, last_recalc_date (= data date), and TASKPRED aref/arls when field exists.
Tests: tests/cpm.test.ts — chain FS/SS/FF/SF with lags (incl. negative), constraints each type,
milestone placement, in-progress retained vs override (pred unfinished), completed pred with lag past DD,
loop abort, must-finish-by negative float, free float, longest path flag, LOE, external dates.
