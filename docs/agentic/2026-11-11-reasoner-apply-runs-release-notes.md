# The schedule reasoner's apply: one number per run, and no run on a schedule in progress (next release)

**What changed for the platform.** The clone's own `optimize_schedule` with `apply` (and the Optimise screen's Apply) now follows the rule the owner set on 2026-11-11, the one the platform applies to its stored schedules, with the same custom-field names and types. A file applied by either is continued correctly by the other. Code: `core/analysis/whiq-fields.ts` (`whiqRunOps`, `runNumbers`, `reasonerRefusal`; both the tool's apply and the screen's Apply call `writeWhiqFields`), `mcp/analysis.ts`, `core/analysis/hrm.ts` (`proposalOps`); tests: `tests/reasoner-apply-runs.test.ts`, `tests/analysis-hrm.test.ts`, `tests/screens-run-as-tools.test.ts`.

**The rule.** The run's numbers become the activities' durations. The numbers they replace move into custom fields, like columns added to the activity list per run:
- `WHIQ original duration (d)` (number): the duration an activity had before its first change. Never changes once set.
- `WHIQ run <N> duration (d)` (number): from the second run on. An apply that overwrites an activity that already has an original puts its old duration here, N = the number of the run being applied minus 1.
- `WHIQ duration change (d)` (number): current duration minus the original, on every activity that has an original, recomputed at each apply (a duration edited by hand shows too).
- `WHIQ change note` (text): the latest run's note. An activity the latest run does not change keeps its duration and its note.
- `WHIQ leveling rank` (integer; an existing number field of that name is accepted): the latest run's place in the leveler's order. A rank the latest run does not give is removed.
An activity a run does not change moves nothing: its cell in the run column stays empty. All of it is in the apply's one undoable change; undo takes back the values and the field the apply declared.

**Which run it is.** A project's first apply is run 1 and declares no numbered field. A later apply is run K = (the highest N among the declared `WHIQ run <N> duration (d)` fields, 0 when none) + 2 and declares `WHIQ run <K-1> duration (d)` whether or not any cell is filled. A project is in its first run when the file does not declare `WHIQ original duration (d)`. Custom fields are global to a P6 file, so in a file with several projects a project is also in its first run when none of its activities carries an original. Every later run declares a column at least as high as its own K-1, so a project's next K is always above it. A project with the four fields from the earlier apply simply has an original: its next apply is run 2. A run that changes no duration (ranks only) declares no numbered field. In a file with several projects the run number is the file's, not the project's: a project's run can skip numbers, and `WHIQ run N duration (d)` holds the duration an activity had before the file's run N+1 was applied to it. A project with saved baselines is one project (a baseline is a copy of it, tagged `_baseline_of` or, in an XER read without that tagging, a project row whose `orig_proj_id` names another project of the file); baseline activities never count as progress and get no field.

**`crash_schedule` apply follows the same rule** (the older rule, `whiqFieldOps`, is deleted): the number a crash replaces moves into the original (an activity's first change) or `WHIQ run <K-1> duration (d)`, the crash is a run in the numbering and declares its column, and a crash and the reasoner can be applied to one project in any order (reasoner 10 to 8, crash 8 to 6, reasoner 6 to 4 gives original 10, run 1 = 8, run 2 = 6, current 4). Crashing still works on a schedule in progress, and for an activity under way the duration is its remaining duration, as before; its `WHIQ duration change (d)` is written only when a run changes it (progress moving the remaining duration is no edit). Crashing gives no leveling order, so it leaves the `WHIQ leveling rank` an earlier reasoner run wrote as it is (the ranks still describe the order that run gave the leveler); the reasoner removes the ranks it does not give. `objective: min_crash_cost` with `apply` is the same crash.

**Refusal.** The reasoner does not run on a schedule in progress. `optimize_schedule`, every run, with or without `apply`, either objective, and the screen's run, are refused before anything runs when the project is in progress: an activity (not a WBS summary) whose status is in progress or complete (`TK_Active`, `TK_Progress`, `TK_Complete`), or with an actual start or finish, or with percent complete above 0 as P6 defines it for the activity's own percent-complete type (a Duration or Units type activity that has not started is at 0 whatever numbers the row holds: a remaining duration below the original, or a physical percent left on it, is no progress; any other type reads the physical percent), or a data date (`last_recalc_date`) after the planned start (`plan_start_date`), compared as days, strictly after. This is ONE rule with the White Hat IQ platform's import (its `taskProgress`), so a file and the schedule imported from it get the same answer (changed in whiq-v0.1.68; v0.1.67 also counted a physical percent of any type and a shortened remaining duration). Error code `schedule_in_progress`:
- message: `optimize_schedule: nothing was run. The schedule is in progress (N activities have actual dates or progress; the data date D is after the planned start S), and the schedule reasoner plans only work that has not started.`
- hint: `To shorten the remaining work of a schedule in progress, use crash_schedule. To level resources on work in progress, use level_resources.`
Because of this the reasoner's apply no longer writes remaining durations: every change is a duration.

**The platform** implements the same rule for its stored schedules (`REASONER_UDF`, `reasonerRunName`, `reasonerRunNo`, `isReasonerCopy`, `applyReasonerChanges`, `refuseInProgress`): one project per schedule there, the file-wide declaration test here.
